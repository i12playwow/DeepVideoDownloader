## Release checklist — confirm a green boot-verify drill before ANY 1.3.x dist build
Before bumping the version or running `npm run dist`, a green real-app drill is MANDATORY — `npm test` and `npm run check` are static/offline gates and do not boot the app. A drill run is green when it is **8/8 checks, exit 0**. Two acceptable ways to get one (either counts):
1. **Local (fastest):** `npm run boot-verify` from a clean tree (no `config.json`; the script aborts if port 8766 is busy or `config.json` exists without `--force`). Takes ~5–6 min: boot/WS hello on isolated port 8766, byte-exact download, schedule-window gating (runtime-derived closed window), site-rule bypass + folder override, auto-retry timing, cap exhaustion, CDP-driven budget reset, fair per-host pump. The prod app on 8765 is never touched; the sandbox is cleaned up on success.
2. **CI:** dispatch **Actions → boot-verify (optional) → Run workflow → master** (or `POST /actions/workflows/boot-verify.yml/dispatches {"ref":"master"}`). Watch it through to `success` — a skipped/locked run (e.g. the account billing lock seen on run 34074382106) does NOT count as green.
If the drill fails on a release candidate, treat it as a release blocker: download the CI `boot-verify-sandbox` artifact (or keep the local `scripts/bv-*` sandbox with `--keep`) and fix the engine before shipping — do not re-run until green. Record the run (local output or CI run URL) in the release notes for that 1.3.x version.
- **Enforcement:** `npm run check` includes `scripts/check-release-drill.js`, which FAILS any commit that bumps the package `version` without a linked green drill in its commit message — either a GitHub Actions run URL (`github.com/<owner>/<repo>/actions/runs/<id>`) or a local marker line (`drill: 8 checks: 8 passed, 0 failed`). The marker must quote equal pass/total counts with at least 8 checks (a stale 7-check summary from an older drill revision is rejected). Non-bump commits and git-less/shallow environments skip the gate.
- **Artifact enforcement:** `npm run dist` ends with `scripts/check-dist-artifact.js`, which FAILS the build unless `dist/win-unpacked/resources/ffmpeg.exe` exists and is > 50 MB (the real bundle is ~98 MB; a shim is ~0.4 MB). electron-builder exits 0 even when an extraResources source is missing — that is exactly how 1.3.10's first installer silently shipped without bundled ffmpeg — so never trust a green dist exit code alone, and never distribute an installer that failed this gate.
- **Master merges go through the gated workflow — do NOT hand-drive protection config.** Master's protection requires only the `tests` check (strict, app_id 15368), but a NON-required failing check from the `cloudflare-workers-and-pages` app (`Workers Builds: consoleapp1`) poisons GitHub's mergeability to `state: blocked` even with `tests` green (the ghost-required-check bug; the association was refreshed 2026-09-08 but can re-appear on any repo-wide check change). Merging a PR now means: (1) dispatch **Actions → merge-pr (tests-gated)** with `pr=<number>` and `confirm=YES` (the approval gate), (2) the workflow verifies the `tests` check is completed+success on the PR head — that is the AUTHORITATIVE gate, everything else is ignored — and squash-merges, (3) it first tries a plain API merge (no protection churn when GitHub is sane) and only falls back to capture → delete → merge → restore when the phantom blocks, restoring byte-identical from the live capture. The workflow needs the repo `ADMIN_TOKEN` secret (admin PAT; branch-protection endpoints refuse GITHUB_TOKEN). A human must still dispatch and type the gate; nothing is automated past the merge itself.
- **Protection-restore read-back (semantic, never shallow):** any branch-protection dance (including the merge workflow's fallback) MUST end by reading the LIVE protection object back and asserting semantics, not by shallow-comparing JSON. Object-wrapped booleans are truthy in JS: `allow_force_pushes: { enabled: false }` makes `bool(obj) === true`, so a naive compare silently re-enables force-pushes — the 4f66d3e restore caught exactly that. Verify the read-back fields explicitly: `allow_force_pushes.enabled === false`, `enforce_admins.enabled === true`, `required_linear_history.enabled === true`, no `required_pull_request_reviews`, and the required status-check names match the captured config, before declaring the dance done. Also: the protection PUT body MUST include `required_pull_request_reviews: null` and `restrictions: null` (the API 422s without them), and the capture's per-field `enabled` values must round-trip (don't flatten to hardcoded defaults).
