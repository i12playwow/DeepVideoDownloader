## Packaging gotchas
- electron-builder STRIPS `scripts` and `build` from the `package.json` baked into `app.asar`. They exist only on disk — never trust the asar copy.
- `build.asarUnpack: ["extension/**/*"]` is REQUIRED: `session.loadExtension` cannot load from inside asar, so the extension must be on a real path (`app.asar.unpacked/extension`).
- After bumping `package.json` `version`, rebuild + reinstall.

## Built-in browser = BrowserView (NOT <webview>)
`<webview>` (OOPIF) ignores its CSS box and renders at the 300×150 default (only ~top 1/5 of the page shows). `BrowserView.setBounds()` is deterministic — never revert to `<webview>`.
- Tab state lives in main.js: `bvAddTab`, `bvActivate`, `bvCloseTab`, `bvCloseTabForUrl`, `bvPositionActive`, `bvPushTabs`, `bvPushNav`.
- Renderer `browser.html` is pure UI: sends `bv-new-tab`/`bv-close`/`bv-activate`/`bv-navigate`/`bv-back`/`bv-forward`/`bv-reload`/`bv-content-rect` via `browser-preload.js` (`window.api`); listens for `browser-tabs-update`/`browser-nav-state`.
- BrowserViews share `session: browserSession()` = `persist:deepgrab-browser` (the session the extension loads into), so HLS detection works inside them.
- Finished-tab auto-close: `pushUpdate` → `bvCloseTabForUrl(item.referer || item.url)`.

- **CF auto-click MUST click once then wait ~6s (cooldown via `cfLastClick`) — do NOT click every tick.** Hammering re-triggers Cloudflare Turnstile in an infinite loop. After ~6 attempts it logs "please solve manually" and stops.
- For HLS to appear, the user MUST set **Best only = OFF, Min MB = 0** in the extension popup.
- `manifest.json` `all_frames:true` so the CF auto-click fires inside the challenge iframe.
- **Extension relay E2E verified (2026-08-29)**: source detection + WS relay are proven live — surrit masters (`SIMW-010`, `LUXU-1892`, `SDMM-238` …) captured with page-title filenames, relayed, enqueued, went `running` (family dedupe still correctly dup's old hashes). Ext host WS confirmed: the one-click real-Chrome session's network-service proc holds ESTABLISHED on 127.0.0.1:8765.
- **CF-walled HLS is cookie-gated, NOT a hard wall (validated 2026-08-29)**: cookieless headless probes of surrit.com masters 403, but the app's `cookieHeaderFor` bridge reads the built-in browser session, so once that session holds surrit CF clearance the engine downloads fine. **Full E2E proven live**: `LUXU-1892` surrit master → WS relay → engine HLS → ffmpeg remux → a 2.2GB 1920x1080 (01:15:33, h264/aac) `.mp4` landed in `Downloads\DeepGrab`; `SIMW-010` was mid-remux when the app was killed (temp segs since swept). Warning: a `running`-status recv=0 spell (~1-2 min) is normal — it's the master/variant probe + queue fill, NOT a stick. If clearance lapses, the run 403s → requires-browser → user re-solves in the built-in browser → extension re-captures. Don't chase headless TLS-fingerprint tricks for surrit — the cookie bridge already clears it.
- **Ad-polluted HLS playlists (shipped 1.2.7)**: `hls1/hls2.turbosplayer.com/…/master.m3u8` (pulled by `cdn2.turboviplay.com` redirects behind sextb pages) are media playlists whose "segments" are `tiktokcdn.com/…/ad-site…image` URLs — ad-images injected INTO the HLS. They parse fine (`#EXTM3U`, `TARGETDURATION:5`) so `isHls`/content.js surface them. Since 1.2.7 the engine rejects them: `lib/hls.js` `isAdSegmentUrl()` (pure, exported) flags tiktokcdn `ad-site` hosts, `/ad-site-` paths, and image-shaped segment URLs (`~tplv-…image`, `.jpg/.png/.webp/.gif/…`) — real signed tiktokcdn `.ts`/`.m4s` segments (supjav/turbovidhls PNG-decoy case) never match; `downloader.js runHls` filters ad segments out of the queue (`videoSegs`) and throws `HLS: playlist segments are all ad-images (ad-polluted stream)` when a playlist has NO video segments (no "cf-" → no retry storm). Mixed playlists keep their real segments and drop the injected ads. Harness S; `check.js` + `test-hls.js` cover the pure guard.
- **How the extension grabs download URLs (3 independent layers → one `tryCapture`)**:
  1. **DOM scan (content.js)**: `scanVideoElements` (queries `<video src>`, `<source src*='.mp4'>`, `data-src/.mp4` attrs via `DEFAULT_VIDEO_SELECTORS`), `scanPageLinks` (any `<a href>` that matches), plus the supjav/sextb scanners (`scanSupjavList` → captures movie-*page* URLs as `kind:"link"`; `extractSupjav` → captures the `supjav.php?l=` player iframe). Periodic rescan re-runs for lazy-loaded content.
  2. **Network interception (content.js `hookNetwork`)**: wraps `XMLHttpRequest.open` + `window.fetch` (flags both the request URL and the post-redirect `resp.url`), and listens for `loadedmetadata`/`canplay`/`play` to read the `<video>` element's real `currentSrc`. Catches URLs the site never puts in the DOM.
  3. **webRequest (background.js)**: network-layer, works even in suspended/background tabs — `onBeforeRequest` flags any `NET_VIDEO_RE` (`\.(mp4|…|m3u8)`) or `ST_GETVIDEO_RE` (streamtape `get_video?`); `onHeadersReceived` fills `size` from `content-length`/`content-type`.
  - **Gate**: every URL passes `looksLikeVideoUrl()` (content.js:147) — media extension, streamtape `get_video`, or path with `/video/|/stream/|/media/|/playlist/`. `isAdUrl` always rejects ad hosts; `blob:` and non-http(s)/extension-scheme URLs dropped. All layers funnel into `tryCapture` → `found` list (size 0 → filled later by HEAD probe + status) → `video-found` → `maybeAutoDownload` → `sendToDesktop` → WS `download` → engine `enqueue`.

## Domain logic (missav / supjav) — all in `lib/resolvers.js`
- MissAV regex `/missav\d*\.(ws|ai|com|live|xyz)/i`; `resolveMissav` fails fast `requires-browser` (message avoids "cloudflare"/"cf-" so `downloader.js` retry loop is NOT triggered) → opens URL in built-in browser.
- Supjav `SJ_PLAYER_RE = /(?:supjav|supremejav)\.(?:com|ph|net)[^"'\s]*\bsupjav\.php/i` routes the player iframe to `resolveSupjav` (→ direct HLS).
- WS `download` enqueues every `kind:"link"` AND `kind:"iframe"` source (never `server`).
- **sextb (validated 2026-08-27)**: `sextb.net` is directly reachable (no proxy) but serves a Cloudflare **managed challenge** interstitial (`_cf_chl_opt`, `cType:'managed'`, title "Checking your browser...", `lang="vi"`) — the classic "Just a moment"/`cf-challenge` detector MISSED it, so JAV pages failed with a confusing "no supjav iframe or direct m3u8/mp4 source found" instead of routing to the built-in browser. Detect via `lib/errors.js` `isCfChallengeHtml()` (title + container + `cf-chl` markers); used by `resolveJavAggregator`, `resolveJable`, `resolveMissav` and the autoloop userscript. Once in the built-in browser the user solves CF and the extension captures the m3u8.
- **sextb movie pages are never lists (validated 2026-08-28)**: sextb/supjav MOVIE pages carry a related-thumbnail grid (≥3 movie links), so `resolveJavAggregator`'s `listUrlCheck || page1Links.length >= 3` heuristic misread them as LIST pages → the page self-marked `done` recv=0 (junk history row) and enqueued its related links (storm multiplier). Since 1.2.6 only LIST-url-shaped pages expand (`listUrlCheck`, or non-movie-shaped pages with ≥3 links); movies never expand. A fetched movie page that yields no source now throws `requires-browser` (message keeps "cf-" out) so the built-in browser + extension can capture instead of failing silently. Harness R.
- Shared helpers: `lib/http.js`, `lib/hls.js`, `lib/names.js`, `lib/errors.js`.
- **sextb `/feed` blacklist (validated 2026-08-27)**: sextb pages carry WordPress nav links (`<a href="/feed">`, `/rss`, `/wp-json`, …) that the old `isSextbMoviePath` didn't reject → ~1500 `/feed` URLs got enqueued and errored with "no supjav iframe..." noise. Fixed in `extension/content.js` (`isSextbMoviePath`/`isSupjavMoviePath` blacklist adds `feed|rss|atom|api|ajax|wp-json|wp-content|wp-admin|wp-includes|trackback|xmlrpc|author|date|embed|oembed`) and `downloader.js` module-scope `isJunkNavUrl()` (last path seg in feed/rss/atom/sitemap.xml/sitemap/robots.txt/favicon.ico) used by `addPending` (skip) + `enqueue` (throw `Unsupported URL`).
- **supjav.com movie pages are a hard CF-managed wall (validated 2026-09-02)**: `https://supjav.com/452555.html` (and every raw movie-page URL like it) always fetches 403 "Just a moment..." with `turnstile=true`, `managed=true`, `metaRefresh=true` — a Cloudflare **managed Turnstile** interstitial. Headless Node cannot clear it AND the Electron built-in browser cannot either (Cloudflare rejects the embedded-Chromium runtime; a *manual* Turnstile click in the built-in browser also never completes). So every such enqueue fell through to a STUCK built-in tab → `requires-browser` error. The app-killing supjav crawl storm (hundreds of `453xxx.html`/`454xxx.html` enqueues all erroring `requires-browser`) was exactly this. Fix (1.3.x): `lib/resolvers.js` `isCfwalledSupjavMovie(u)` (host exactly `supjav.com`, pathname `/\d{3,}\.html?$/`; supremejav/sextb untouched) is enforced at `enqueue` (throws targeted `Unsupported URL` message pointing to real Chrome+extension) + `addPending` (skip) + `ws-bridge.js` (filters doomed sources out of a `download` batch so a movie page next to a player URL never aborts the good one; all-blocked batch replies with the actionable CF message). The ONLY working supjav route is the Deep Grab extension relaying the `supjav.php?l=` player URL out of a **CF-cleared real-Chrome** tab — the player URL (and `/list`) do NOT match the predicate, so capture still works. Harness M2/M3. Do NOT "fix" this by making the built-in browser open supjav tabs — that path can never clear the managed Turnstile.
- **HLS variant→master resolution (validated 2026-08-28)**: MissAV players (surrit.com) pull `…/<hash>/360p/video.m3u8` DIRECTLY, so captures pinned the 360p stream (406MB) plus downloaded the master `…/<hash>/playlist.m3u8` (997MB) separately. Two fixes in the download engine:
  1. `downloader.js` `_probeMasterPlaylist` (used by `runHls`): when the enqueued playlist is a media variant (no `#EXT-X-STREAM-INF`), probe sibling `playlist/master/index.m3u8` one dir up and switch to the master so the engine picks the HIGHEST variant. Best-effort, silent fallback.
  2. `lib/hls.js` `matchHlsMaster(url)` (pure): maps a variant URL to its family master URL(s); `downloader.js` `isDownloaded` + `_hlsMasterInFlight` treat a variant as duplicate when its master is already downloaded or queued/running → no more 997MB+406MB double download. Only `video.m3u8` filenames or quality-dir (`<N>p`/hls/sd/hd…) shapes qualify; masters (`playlist|master|index|manifest`) never dedupe against anything.
- **Autoloop crawl-storm / nav-slug guardrail (validated 2026-08-28)**: the Tampermonkey sextb autoloop userscript crawls list pages and enqueues hundreds of items/min. Its junk came through TWO gaps, both closed with a "movie slugs always carry a digit" rule:
  1. `extension/content.js` `isSextbMoviePath` now blacklists `invite-ads|private|genres|new-releases|dmca|download|slut|hot|best|most|censored|uncensored` AND requires a digit in the last slug segment.
  2. `downloader.js` module-scope `isJavNavPage(u)` (same digit/nav rule, sextb/supjav/supremejav hosts only; `.html` pages always pass) is enforced in `enqueue` (throws `Unsupported URL`) + `addPending` (skip); exported for tests. The runaway manifested as hundreds of `done`/`running` items at recv=0 plus repeated nav-slug enqueues, hanging `chrome.exe` (AppHangB1 in Event Log) and exiting the app. **DO NOT add a per-host tab-open cap to `lib/browser-open.js`** — distinct movie pages on the same host each legitimately need their own tab to expose their m3u8 (harness section D guards this).
  3. **Storm source is a Tampermonkey userscript (validated 2026-08-28)**: the app-killing crawl is the *user's* Tampermonkey sextb autoloop (sends `download` over its own WS connection, continuously opening movie tabs) — NOT the app. The shipped `extension/supjav-autoloop.user.js` only matches `supjav.com/*` and is off by default (`supjav.loop.enabled`), so it is NOT the storm. The extension itself cannot storm: `maybeAutoDownload` requires `grabOn` (pressing ▶ Start), which is memory-only so a fresh page load starts OFF. Because an autoloop crawls *real* movie slugs, it is indistinguishable-by-design from a user bulk-pasting movies, so the app can only THROTTLE it, never block it selectively. Durable fix remains the USER disabling the sextb autoloop in Tampermonkey.
  4. **Throttle is GLOBAL, not per-socket (validated 2026-08-28)**: the crawl morphs — one wave hit with `https://Mouth`, `https://On`, … single-WORD dotless-host URLs (per-tab userscript builds `https://` + page words). A per-socket throttle was bypassable because each tab's userscript uses its OWN WS connection. Two fixes in 1.2.4: `main.js startWsServer` creates ONE shared `makeCrawlThrottle()` instance across all sockets (cold burst passes, sustained crawl capped at `sustainedPerMin`=4/min after `burstWindowMs`=8s, resets after `idleResetMs`=10s quiet), and `downloader.js` `isJunkHost(u)` rejects dotless single-word hostnames (`https://Mouth` → no dot → `Unsupported URL`, loopback/localhost always pass) in `enqueue` + `addPending`. Both verified live (word URLs → instant `Unsupported URL` while `https://localhost:8765/x` still accepted). `isJunkHost` exported; harness section P.
- **Live HLS E2E proof (validated 2026-08-28)**: enqueued the mux.dev master `https://test-streams.mux.dev/x36xhzz/x36xhzz.m3u8` in the running app → probe/segment flow picked the HIGHEST variant (url_8 1080p) → 64 real .ts segments downloaded → real ffmpeg remux → ONE 465MB `live-master.mp4` (verified `1920x1080`) — no 360p/duplicate sibling file. Applied in `enqueue` (throws `Unsupported URL`) + `addPending` (skip), and in the extension's `sendToDesktop` so junk never leaves the browser. Observed junk (history): github releases/accounts, ai.google.dev/aistudio/policies/mail, firecrawl signin redirects, jdownloader, violentmonkey, internetdownloadmanager, vn-zoom, webextension, and `https://1`–`https://8`. - **Auto-titles from URL (shipped 1.3.7)**: many supjav/missav/sextb bulk-add items reached the engine with no title and a non-streamtape referer → `effectiveTitle` was empty → every file named `video.mp4`. ## Cookie bridge / proxies
- `main.js` `cookieHeaderFor`/`gatherCookieHeader` build a `Cookie` header from the `persist:deepgrab-browser` session; `downloader.js` attaches it via `item.cookieHeader` + `cookieProvider` on all 5 request sites (`_reqHeaders`).
- Proxies default `http://127.0.0.1:7890` + `socks5://127.0.0.1:1080` (configurable in `config.js`).
- `BROWSER_UA` (main.js) is a real Chrome UA so Cloudflare serves a solvable challenge.
- **ffmpegPath must resolve in the app's OWN environment (validated 2026-08-28)**: the installed app's `%APPDATA%\deep-video-downloader\config.json` defaulted to `"ffmpegPath": "ffmpeg"`, which silently fails (`ffmpeg not found`) for any HLS download when the app is NOT launched from a shell whose `PATH` carries ffmpeg (e.g. Start-menu launch). The machine's ffmpeg lives at `C:\Program Files\JavLuv\ffmpeg.exe` (no `ffprobe`; use `ffmpeg -i <file>` stderr to read resolution). Since 1.2.5 this is self-healing: `downloader.js` `findFfmpeg(config)` (module-scope + manager-cached via `_resolveFfmpeg`) probes, in order, config.ffmpegPath → `resourcesPath\ffmpeg.exe` (future electron-builder bundle) → `$FFMPEG_PATH` → `C:\Program Files\JavLuv\ffmpeg.exe` → `C:\Program Files\ffmpeg\bin\ffmpeg.exe` → `ffmpeg`, returning the first that spawns `-version` cleanly (verified: clean-PATH + default config resolves to JavLuv). Exported for tests; harness section Q. A working `ffmpegPath` in config still wins, so no user config is required on fresh installs.
- **Supjav capture → streamtape get_video token expiry fix (validated 2026-09-03)**: the supjav capture → `resolveSupjav` → streamtape embed → signed `get_video?id=...&expires=...&ip=...&token=...` chain is proven live (393 player-URL entries captured with real titles in history). But streamtape's signed `get_video` token is per-IP and near-instantly expiring, so the engine's probe returned `text/html` and the engine misclassified it as a terminal `not-video` error — 347 of 393 items errored with `Not a video: server returned text/html at https://streamtape.com/get_video?id=...`. Fix in `downloader.js`: new `isSignedGetVideoExpired(item, err)` helper (true when `_resolvedUrl` is a streamtape/fstape `get_video` URL and the error category is `not-video`) is wired into `_runGuarded`'s refresh gate (`!isExpiredError(err) && !isSignedGetVideoExpired(item, err) throw err`). A streamtape get_video returning HTML is now treated as an expired signed token → the engine re-resolves the original supjav player URL (`refreshSourceUrl` returns `item.url` since the referer is supjav, not streamtape) for a fresh token, instead of dying terminal. Bounded by `maxRefresh` (default 2) — honest error if streamtape keeps returning HTML. Test: `test-hls.js` P2 section `isSignedGetVideoExpired` (7 asserts); test-hls.js 51 passed, test-e2e-harness.js 149 passed.
